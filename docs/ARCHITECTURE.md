# Архітектура та потоки даних

## 1. Загальна схема

```
 Telegram (Bot API)                       Авторизований клієнт оператора (канал B, вимкнений за замовчуванням)
   getUpdates (timeout=0)                   examples/push_reader.py  (лише читання)
        │                                          │ POST /p/actions/monitor.ingest  (scoped-токен)
        ▼                                          ▼
 ┌──────────────────────────── Collector  (olian/monitor.py) ──────────────────────────────┐
 │ перевірка джерела (погоджене? active?) · нормалізація · ідемпотентність (source,msg_id)   │
 │ статуси джерел: active | paused | unavailable | auth_error · backoff · повага до retry_after│
 └───────────────┬───────────────────────────────────────────────────────────────────────────┘
                 ▼
   Рівень 1: правила з БД (фрази, require_any, all_of, виключення)      ── без збігу: зберігається як `received`
                 ▼
   Дедуплікація: повтор / близький дубль (SimHash + Jaccard) → збіг до наявного ліда, без кваліфікації
                 ▼
   Черга в БД: tg_messages.state = pending   (повтори при збої моделі, потім резерв правил + `needs_review`)
                 ▼
   Рівень 2: Qualifier (olian/qualify.py)  rules | hybrid | llm   — без інструментів, текст = недовірені дані
                 ▼
   rejected (реклама/спам/не запит)   або   лід: new | review    (+ дедуп за автором і категорією)
                 ▼
   Notifier → оператору            Панель /admin · REST · MCP        Звіти · CSV · оцінка якості
                 ▼
   Модуль контакту (olian/outreach.py): за замовчуванням ЗАКРИТИЙ для лідів з моніторингу
```

## 2. Модулі

| Файл | Відповідальність |
|---|---|
| `olian/monitor.py` | джерела, правила, збір (Bot API), конвеєр, дедуплікація, ліди/статуси, звіти, експорт, оцінка, очищення, видалення |
| `olian/qualify.py` | нормалізація, SimHash/Jaccard, пошук фраз, `RuleQualifier`, `LLMQualifier`, `Qualifier` (rules/hybrid/llm) |
| `olian/channels.py` | клієнти Telegram/WhatsApp; `TelegramError` з `retry_after`; токени не потрапляють у повідомлення помилок |
| `olian/outreach.py` | контакт: підстава, стоп-лист, ліміти, аварійний вимикач, відправники |
| `olian/facade.py`, `actions.py` | єдина точка дій: ролі, scoped-токени, журнал дій (`monitor.*` закриті для агента) |
| `olian/api.py`, `static/` | REST, MCP, панель із суворою CSP |
| `olian/migrations.py` | версіоновані міграції (`schema_version`) |
| `olian/app.py` | складання, воркери: швидкий цикл збору (5 с) і повільний (30 с: перевірка джерел, очищення) |

## 3. Стани

**Повідомлення** (`tg_messages.state`): `received` (немає збігу) → `pending` → `qualified` (створено лід) |
`linked` (додано до ліда того ж автора) | `rejected`; `duplicate` (повтор/близький дубль, без кваліфікації).

**Лід** (`tg_leads.status`): `new` / `review` (низька впевненість або модель недоступна) → `relevant` | `irrelevant` →
`processed`; або `excluded`. Кожна зміна пишеться в `tg_lead_history`; повторні збіги в `tg_lead_hits` (`repost`,
`near_duplicate`, `same_author`).

**Джерело** (`tg_sources.status`): `active` ⇄ `paused` (оператор); `unavailable`, `auth_error` (система/клієнт, з причиною;
повернення лише рішенням адміністратора).

## 4. Модель даних

Міграції: v1 базова схема Olian; v2 моніторинг (`tg_sources`, `tg_rules`, `tg_messages`, `tg_leads`, `tg_lead_hits`,
`tg_lead_history`, `tg_state`, `leads.consent`); v3 (`tg_rules.require_any`, стан відправників). Ключові обмеження:
`UNIQUE(source_id, tg_message_id)`; каскадні зовнішні ключі від проєкту; `tg_leads.source_id ON DELETE SET NULL`
(видалення джерела не знищує ліди). Усе фільтрується за `project_id`: проєкти ізольовані.

## 5. Одночасність і надійність

* SQLite у режимі WAL, один процес; воркери: збір (потік), обслуговування (потік), HTTP. Кожне повідомлення ідемпотентне.
* Перезапуск не губить дані: `pending` лишається в БД, зміщення `getUpdates` зберігається лише після обробки.
* Збій моделі: до `max_attempts` повторів; далі резервний результат правил з `needs_review` (лід іде в «На перевірці»).
* Масштабування: коли потік або кількість проєктів перевищать можливості одного вузла, наступний крок — PostgreSQL і зовнішня
  черга (див. `ESTIMATE.md`); шар `DB` у `olian/db.py` тонкий.

## 6. Безпека за шарами

Ролі й scoped-токени (фасад) → журнал дій без секретів і без ID авторів → псевдонімізація автора (HMAC із сіллю на проєкт) →
CSP у панелі та `textContent` для недовірених даних → кваліфікатор без інструментів → шифровані резервні копії.
