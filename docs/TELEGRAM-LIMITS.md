# Залежності від Telegram, обмеження та вбудований захист

> Домен Telegram був недоступний під час розробки, тому цифри нижче це орієнтири зі звичайної документації та матеріалів
> замовника (⚠️ перевірити в чинних `core.telegram.org/bots/faq` і `core.telegram.org/api/terms`).

## 1. Що саме використовується

| Виклик Bot API | Навіщо | Частота |
|---|---|---|
| `getUpdates` (`timeout=0`, `allowed_updates=[message, channel_post, my_chat_member]`) | збір повідомлень | кожні ~5 с на проєкт |
| `getChat` | перевірка доступності джерел | раз на 30 хв на джерело, ≤5 за прохід |
| `sendMessage` | сповіщення операторам і відповіді чат-бота | за подіями, з дайджестом |

**Умови отримання повідомлень:** бот отримує всі повідомлення групи, якщо вимкнено Privacy Mode (BotFather) або бот адмін;
повідомлення каналу, якщо бот адміністратор. Читати чужі групи, куди бота не додано, **неможливо** (і ми цього не обходимо).
`getUpdates` не можна поєднувати з вебхуком або іншим споживачем того ж токена (помилка 409, ми її не «б'ємо»).

## 2. Поведінка при помилках (реалізовано й протестовано)

| Сигнал | Реакція |
|---|---|
| Мережа, таймаут, 5xx | повтор з експоненційним відступом 60→120→240→… до 1 год; URL з токеном не потрапляє в помилки |
| 429 `retry_after=N` | пауза рівно N секунд |
| 401 | усі джерела бота → `auth_error`, збір зупинено до зміни токена; жодних інших облікових даних |
| 400/403/404 для чату, бот видалений (`my_chat_member`) | джерело → `unavailable` з причиною; без обхідних шляхів |
| 409 | не конкуруємо з іншим споживачем, пауза 60 с |
| Невідомий чат | повідомлення **не зберігаються**; лише мінімальна підказка «кандидат» для адміністратора |

## 3. Вбудований захист від обмежень і банів

Основний принцип: **не створювати причин для скарг** і **зупинятися раніше за платформу**.

| Захист | Де | Тест |
|---|---|---|
| Автоматичних холодних DM немає: лідів з моніторингу не можна контактувати без записаної підстави | `Outreach.contact_block` | `test_authors_of_monitored_posts_cannot_be_contacted_without_basis` |
| Усі повідомлення лише після схвалення людини; агент може тільки чернетки | `require_approval` | `test_agent_only_drafts_human_approves…` |
| Аварійний вимикач: сигнал ліміту платформи (`PEER_FLOOD`, 429, 131048…) або 3 збої поспіль → відправник `tripped`; без переходу на інший акаунт; увімкнути лише admin | `Outreach.trip/check_health` | `test_platform_limit_signal_trips…`, `test_tripped_sender_needs_an_admin…` |
| Вимикач за скаргами/відписками (≥3 скарг або ≥25% відписок за 7 днів) зупиняє всі відправники проєкту | `check_health` | `test_complaints_trip_everything`, `test_high_optout_rate_trips` |
| Ліміти на людину: ≤3 повідомлення без відповіді, ≥72 год між ними; відповідь людини знімає обмеження | `send_due` | `test_per_person_limits_unless_they_reply` |
| Загальний денний ліміт проєкту, вікно годин, пейсинг, ліміт на відправника | `send_due`, `_pick_sender` | `test_project_daily_cap`, `test_window_caps_pacing_and_rotation` |
| Один відправник на канал Telegram: без ротації/failover | `_pick_sender` | `test_telegram_has_no_account_rotation_or_failover` |
| Глобальний стоп-лист (всі канали), стоп-слова, чернетки й черга скасовуються миттєво | `stop`, `handle_reply` | `test_stoplist_is_cross_channel…`, `test_opt_out_is_final` |
| Футер з відпискою в першому повідомленні (ст. 14 GDPR) | `send_due` | `test_optout_footer_only_on_first_contact` |
| WhatsApp: лише офіційний Cloud API, поза 24 год лише шаблон | `_deliver` | `test_whatsapp_cloud_uses_template…` |
| Сигнали правил створюють ліди без автоконтакту, оператору йде сповіщення | `signals._act` | `test_rule_turns_message_into_lead_but_never_auto_contacts` |
| Токени маскуються в логах | `app.redact` | `test_tokens_never_reach_logs` |
| Сторожовий тест: у коді немає ротації акаунтів, пулу проксі, «прогріву», підміни відбитків | — | `test_no_evasion_features_exist_in_the_code_base` |

## 4. Що свідомо НЕ реалізовано (і чому)

Ротація акаунтів для продовження розсилки після обмеження, пули резидентних/мобільних проксі, підміна відбитків
з'єднання (`initConnection`), «прогрів» акаунтів, придбані сесії, масові DM незнайомцям. Це не захист, а **обхід** антиспам-
системи платформи: він підвищує ризик блокувань усієї «сітки» акаунтів, юридичний ризик (Закон № 480/2004 Coll., GDPR) і
не усуває причину санкцій, якою є скарги отримувачів. Чесна відповідь на «захист від банів»: єдина надійна стратегія це не
робити того, за що банять, і вчасно зупинятися.

## 5. Канал B (клієнт оператора, MTProto)

Лише за письмовим рішенням (ТЗ §10, ADR-1). `examples/push_reader.py`: тільки читання, лише погоджені чати з Olian, одна сесія,
`FloodWait` чекаємо рівно стільки, скільки сказано, втрату доступу/сесії **повідомляємо** й зупиняємось. Файл сесії це пароль
до акаунта: права 0600, не передавати нікому, при інциденті відкликати сесію в Telegram (Settings → Devices). Не використовуйте
основний особистий акаунт. Умови Telegram щодо неофіційних клієнтів і збору контенту потрібно перевірити до запуску.

## 6. Ліміти ботів (орієнтири ⚠️)

≈1 повідомлення/с в один чат, ≈20/хв в одну групу, ≈30/с загалом. Наш обсяг (сповіщення операторам з дайджестом, ≤5 на прохід)
далеко нижче.
