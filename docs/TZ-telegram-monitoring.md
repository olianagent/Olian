# Технічне завдання: моніторинг Telegram і кваліфікація потенційних клієнтів

Версія 1.0 · мова: українська · пов'язаний документ: [`RESEARCH-telegram-lead-systems.md`](RESEARCH-telegram-lead-systems.md)

Ключові слова «ОБОВ'ЯЗКОВО», «ЗАБОРОНЕНО», «БАЖАНО» мають звичайне значення вимог різної жорсткості. Кожна вимога має
ідентифікатор (`FR-` функціональна, `NFR-` нефункціональна, `SEC-` безпека, `CON-` контакт) для трасування в тестах.

## 0. Рішення, закладені в ТЗ (коротко)

| # | Рішення | Підстава (з огляду) |
|---|---|---|
| D1 | Основа: **моніторинг + кваліфікація + рішення людини**. Автоматичних холодних приватних повідомлень немає | Найбільший ризик банів/скарг/права лежить у контакті, не в зборі |
| D2 | Канал збору за замовчуванням: **офіційний Bot API** у групах/каналах, де бот доданий і має право читати | Безпечно для особистих акаунтів; відповідає правилам платформи |
| D3 | Канал B: **приймання повідомлень від авторизованого клієнта оператора** (MTProto) через ізольований інтерфейс. **Вимкнений за замовчуванням**, вмикається лише після оформленого рішення (ADR) | Умови Telegram і правова підстава ще не підтверджені |
| D4 | **Заборонено** ротацію акаунтів для обходу обмежень, маскування відбитків/мережі, «прогрів», придбані сесії, масові DM | Це обхід антиспам-захисту; підвищує юридичний ризик |
| D5 | Модуль контакту **відокремлений** і за замовчуванням закритий: контакт лише за записаною підставою (згода/запит самої людини), зі стоп-листом і аварійним вимикачем | GDPR ст. 6, 14, 21; Закон № 480/2004 Coll. |
| D6 | Мінімізація даних: автор **псевдонімізується**, строки зберігання, видалення за запитом | GDPR |
| D7 | MVP: один застосунок з логічно розділеними модулями (SQLite + фонові воркери); перехід на PostgreSQL/чергу, коли потік це вимагатиме | Простота; Postgres/Redis — етап масштабування |

## 1. Мета

Автоматично відстежувати повідомлення у погоджених Telegram-джерелах, знаходити реальні запити за ключовими словами та
контекстом, зберігати результати в єдиній БД і формувати список потенційних лідів для **ручної перевірки**. Скоротити
ручну роботу пошуку, забезпечити контроль якості та уникнути повторної обробки.

**Не мета:** масова розсилка, збір бази людей «про запас», маскування автоматизації.

## 2. Ролі

| Роль | Може |
|---|---|
| `admin` | Джерела, правила, налаштування, видалення даних, експорт, аудит, параметри модуля контакту |
| `manager` (оператор) | Перегляд і зміна статусів лідів, нотатки, тестування правил, експорт, фіксація результату ручної обробки |
| `viewer` | Перегляд лідів і звітів |
| `system` | Фонові процеси (збір, кваліфікація, очищення) |

Доступ реалізується наявним механізмом проєктів Olian (ролі, scoped-токени, аудит).

## 3. Функціональні вимоги

### 3.1. Джерела та збір

* **FR-1** Адміністратор керує переліком джерел: додати, призупинити, відновити, видалити. Видалення джерела видаляє його
  повідомлення; ліди зберігаються (посилання на джерело стає порожнім).
* **FR-2** Статуси джерела: `active`, `paused`, `unavailable`, `auth_error`; з причиною та часом останнього успіху.
* **FR-3** Канал A (Bot API): `getUpdates` невеликими запитами з відстеженням зміщення; повідомлення з чатів, яких немає у
  списку джерел, **не зберігаються** (лише службовий лічильник та «кандидати» для адміністратора: id/назва чату).
* **FR-4** Канал B (push-інтерфейс): `POST` повідомлень з авторизованого клієнта оператора зі scoped-токеном; та сама
  валідація, дедуплікація й кваліфікація. Вмикається прапорцем `monitor.push_enabled` і потребує ADR (див. §10).
* **FR-5** Зберігаються: `source_id`, `message_id`, дата, текст, посилання на оригінал (якщо є), посилання на автора у
  формі за політикою (FR-23). Не зберігаються: телефони, фото профілю, історія автора, медіа.
* **FR-6** Помилки збору: тимчасові (мережа, 5xx) → повтор з експоненційною затримкою; `429/FLOOD_WAIT` → чекати
  вказаний час; `401` → усі джерела бота в `auth_error`, збір зупиняється до оновлення облікових даних; `403/chat not found`
  → джерело `unavailable`. **ЗАБОРОНЕНО** у відповідь на обмеження підключати інші акаунти чи обходити доступ.
* **FR-7** Періодична перевірка доступності джерел (`getChat`) з помірною частотою; зміни статусу фіксуються.
* **FR-8** Повторне отримання тієї самої події не створює дубліката (ідемпотентність за `source_id + message_id`).

### 3.2. Фільтрація

* **FR-9 (Рівень 1)** Набори правил у БД, керовані без зміни коду: назва, категорія, фрази (з підтримкою префікса `слово*`),
  обов'язкові терміни (`all_of`), виключення, мінімум збігів, вага, вмикання/вимикання. Порівняння регістронезалежне,
  нормалізоване (Unicode, `ё→е`, прибрані посилання/зайва пунктуація), за межами слів.
* **FR-10** Тестування правила на збережених повідомленнях у межах строку зберігання: кількість збігів і приклади.
* **FR-11 (Рівень 2)** Кваліфікація повідомлень, що пройшли рівень 1. Результат: `is_request`, `category`, `service`,
  `score` (0–1), `confidence` (0–1), `spam`, `reason` (пояснення), `qualifier` (чим отримано).
* **FR-12** Режими кваліфікатора: `rules` (детерміновані сигнали наміру/пропозиції/спаму), `llm` (OpenAI-сумісна кінцева
  точка без інструментів), `hybrid` (правила; мовна модель лише для сумнівних випадків, щоб економити токени).
  Збій моделі не втрачає повідомлення: повтори, потім резервний результат правил із позначкою `needs_review`.
* **FR-13** Профіль цільового клієнта (текст) налаштовується в конфігурації та передається кваліфікатору.
* **FR-14** Ознаки реклами/спаму (пропозиції послуг, промокоди, казино, масові посилання) відхиляють повідомлення; воно
  зберігається зі станом `rejected` і причиною, але лід не створюється.
* **FR-15** Текст повідомлення для моделі передається як **недовірені дані** (розмежувачі, інструкція ігнорувати команди
  в тексті); відповідь валідується схемою. Кваліфікація **не має доступу до інструментів** (SEC-9).

### 3.3. Результат, лід і статуси

* **FR-16** Лід містить: `source_id`, `message_id`, `message_date`, `message_text`, `message_url`, `author_ref`, `category`,
  `service`, `relevance_score`, `confidence`, `qualification_reason`, `qualifier`, `status`, `hit_count`, `last_seen_at`,
  `operator_note`, `outcome`, `reviewed_by`, `reviewed_at`, `created_at`.
* **FR-17** Статуси: `new`, `review`, `relevant`, `irrelevant`, `processed`, `excluded`. `review` призначається при низькій
  впевненості. Усі зміни статусів пишуться в історію (хто, коли, з чого на що, примітка).
* **FR-18** Оператор підтверджує/відхиляє лід, залишає нотатку та фіксує результат ручної обробки.
* **FR-19** Сповіщення операторам про нові ліди через наявні канали Olian (з обмеженням частоти та дайджестом).

### 3.4. Дедуплікація

* **FR-20** Рівень 1: те саме повідомлення з того самого джерела (унікальний ключ).
* **FR-21** Рівень 2: однаковий/майже однаковий текст у вікні `window_days` (хеш нормалізованого тексту + SimHash із
  порогом відстані Геммінга). Дублікат не проходить повторну кваліфікацію (економія токенів) і додається як «збіг» до ліда.
* **FR-22** Рівень 3: той самий автор і та сама категорія у вікні `author_window_days` → збіг додається до наявного ліда,
  нового не створюється. Лід у статусі `processed`/`excluded` **не відкривається повторно** (за налаштуванням).
  Історія збігів зберігається (`kind`: `repost`, `near_duplicate`, `same_author`).
* **FR-23** Політика збереження автора `monitor.author`: `hash` (за замовчуванням: HMAC-хеш із секретною сіллю, окремо для
  кожного проєкту), `raw` (лише за оформленої правової підстави), `none`.

### 3.5. Звіти та експорт

* **FR-24** Звіт за період: отримано повідомлень, збігів рівня 1, відхилено (спам/не запит), створено лідів, дублікати,
  помилки; частка підтверджених релевантних серед переглянутих; топ джерел і правил; ряд за днями.
* **FR-25** Експорт лідів у CSV (захист від CSV-ін'єкцій), з фільтрами за статусом/категорією/періодом.
* **FR-26** Оцінка якості на погодженій розміченій вибірці: `precision`, `recall`, `F1`, `accuracy`, перелік помилок.
  Цільовий показник визначається після першого пілотного прогону, а не обіцяється наперед.

### 3.6. Строки зберігання та видалення

* **FR-27** Автоматичне видалення: повідомлення старші за `retention_days` (за замовчуванням 14); ліди старші за
  `lead_retention_days` (за замовчуванням 180). Налаштовується.
* **FR-28** Видалення за запитом суб'єкта: за ID автора (обчислюється хеш) або за конкретним лідом; усе пов'язане стирається;
  дія фіксується в аудиті без персональних даних.

### 3.7. Адміністративний інтерфейс

* **FR-29** Вебпанель (без зовнішніх залежностей, сувора CSP): **Джерела**, **Правила**, **Ліди**, **Звіти**. Доступ за
  токеном проєкту; можливості залежать від ролі. Весь недовірений текст виводиться безпечно (без `innerHTML`).
* **FR-30** Той самий функціонал доступний через REST (`/p/actions/monitor.*`) і MCP; усі дії проходять через фасад із
  перевіркою ролей та журналом дій.

## 4. Модуль контакту (відокремлений від моніторингу)

Мета: **не** отримати можливість писати всім, а дати оператору безпечний, обліковий і законний спосіб відповісти там, де це
дозволено.

* **CON-1** За замовчуванням лід з моніторингу **не може** потрапити в чергу звернень (`cold_contact: blocked`). **Зміна за
  рішенням замовника (v1.1):** адмін може явно дозволити писати авторам (`cold_contact: allowed`); рішення фіксується в журналі, а
  всі обмеження CON-4…CON-8 (стоп-лист, ліміти, вимикач, один акаунт на людину) лишаються обов'язковими.
* **CON-2** Для лідів з моніторингу чернетку/відправлення дозволено лише якщо оператор зафіксував **підставу контакту**
  (`consent`): людина сама попросила зв'язатися, дала згоду, або інша задокументована підстава. Підстава зберігається.
* **CON-3** За замовчуванням оператор бачить: текст, посилання на оригінал, категорію, причину відбору й **дозволені способи
  взаємодії** з конфігурації (наприклад: «публічна відповідь у гілці, якщо дозволяють правила групи»).
* **CON-4** Глобальний стоп-лист проєкту: людина, що відмовилась/вимагає не писати, виключається назавжди для всіх
  каналів і відправників. Стоп-слова розпізнаються у відповідях.
* **CON-5** Обмеження настирливості: максимум звернень на одну людину та мінімальний інтервал; не більше одного відправника
  на канал Telegram (без розподілу навантаження між акаунтами).
* **CON-6** **Аварійний вимикач:** при `PEER_FLOOD`, масовому `FLOOD_WAIT`, зростанні скарг чи заблокованому акаунті
  контактування для відповідного каналу зупиняється до ручного розблокування адміністратором. Заміна відправника ЗАБОРОНЕНА.
* **CON-7** Перше звернення містить інформацію за ст. 14 GDPR (хто, з якого джерела отримав дані, мета, як відмовитись).
* **CON-8** `access_hash`: контакт можливий лише тією сесією/каналом, що має до людини законний доступ (публічне посилання/
  `@username` або спільний чат); передавати ідентифікатори між акаунтами для «дотягування» ЗАБОРОНЕНО.
* **CON-9** WhatsApp/e-mail для комерційних пропозицій — лише офіційні канали (WhatsApp Cloud API із шаблонами) і лише за
  наявності згоди (opt-in).

## 5. Нефункціональні вимоги

* **NFR-1 Надійність.** Збої Telegram, мережі, БД, моделі не руйнують роботу: повторні спроби з відступом, чергу в БД
  (`pending` → `qualified/rejected`), відсутність втрати повідомлень при перезапуску.
* **NFR-2 Ідемпотентність.** Повторна обробка не дублює ліди.
* **NFR-3 Спостережуваність.** Структуровані логи без секретів, `/health`, лічильники помилок джерел, журнал дій.
* **NFR-4 Продуктивність (орієнтир MVP).** ≥ 20 повідомлень/с рівня 1 на одному ядрі; кваліфікація асинхронна; фронт панелі
  без важких залежностей.
* **NFR-5 Переносимість.** Docker Compose; SQLite із WAL; міграції схеми з версіонуванням; план переходу на PostgreSQL.
* **NFR-6 Конфігурація без коду.** Правила, пороги, режими, строки — у конфігурації/БД.

## 6. Безпека та приватність

* **SEC-1** Жодних секретів у коді/логах; токени з змінних середовища або конфігурації з обмеженими правами; маскування
  токенів Telegram у логах.
* **SEC-2** Ролі й scoped-токени; адмін-ключ окремо; журнал адміністративних дій (хто, що, аргументи без секретів).
* **SEC-3** Передача даних лише по TLS (зворотний проксі); резервні копії шифруються ключем (`OLIAN_BACKUP_KEY`).
* **SEC-4** Сесії MTProto (якщо канал B буде затверджено): файли лише на стороні клієнта оператора, шифроване сховище,
  доступ за принципом мінімальних прав, відкликання сесій у разі інциденту. **Не передавати розробникам/операторам.**
  Основний особистий акаунт для автоматизації ЗАБОРОНЕНО використовувати.
* **SEC-5** Ротація секретів: перевипуск токенів API без простою; відкликання окремих токенів.
* **SEC-6** Мінімізація: збір лише потрібних полів (FR-5), псевдонімізація (FR-23), строки (FR-27), видалення (FR-28).
* **SEC-7** Панель: суворий CSP, жодного `innerHTML` з даних, перевірка прав на сервері.
* **SEC-8** CSV-експорт нейтралізує формули (`= + - @`).
* **SEC-9** Захист від prompt injection: недовірений текст у розмежувачах; кваліфікатор без інструментів і без доступу до
  фасаду; результат валідується; довжина обмежена.
* **SEC-10** Окремі токени для бота моніторингу та бота чату (не використовувати один токен двічі).

## 7. Архітектура

```
 Telegram (Bot API)        Авторизований клієнт оператора (канал B, за ADR)
        │ getUpdates                       │ POST /p/actions/monitor.ingest (scoped-токен)
        ▼                                   ▼
   ┌────────────────── Collector (olian/monitor.py) ──────────────────┐
   │ нормалізація · ідемпотентність · статуси джерел · backoff        │
   └───────────────┬──────────────────────────────────────────────────┘
                   ▼
   Filter L1 (правила з БД) ──► Dedup (hash+SimHash) ──► queue: pending
                   ▼
   Qualifier (olian/qualify.py): rules | llm | hybrid  (без інструментів)
                   ▼
   Lead store + история статусів + hits ──► Notifier ──► оператор
                   ▼
   Admin UI / REST / MCP (фасад: ролі, аудит) ──► звіти, експорт, оцінка
                   ▼
   Contact module (olian/outreach.py): лише за підставою, стоп-лист, вимикач
```

Модулі й файли репозиторію:

| Модуль | Файл | Примітка |
|---|---|---|
| Міграції схеми | `olian/migrations.py` | версіонування, повторювані міграції |
| Collector, джерела, правила, дедуп, ліди, звіти, очищення | `olian/monitor.py` | |
| Кваліфікація, нормалізація, SimHash | `olian/qualify.py` | |
| Telegram API (помилки з `retry_after`) | `olian/channels.py` | |
| Дії фасаду `monitor.*` | `olian/actions.py` | ролі та аудит |
| Вебпанель | `olian/static/admin.*`, маршрути в `olian/api.py` | |
| Захист контакту | `olian/outreach.py`, `olian/signals.py` | consent, один відправник Telegram |
| Резервні копії/шифрування | `olian/cli.py` (`olian backup`) | |

## 8. Модель даних

Нові таблиці (міграція v2): `tg_sources`, `tg_rules`, `tg_messages`, `tg_leads`, `tg_lead_hits`, `tg_lead_history`,
`tg_state`; зміна: `leads.consent`. Ключові обмеження: `UNIQUE(source_id, tg_message_id)`; зовнішні ключі з каскадним
видаленням від проєкту; `tg_leads.source_id` → `ON DELETE SET NULL`.

## 9. Інтерфейси (дії фасаду)

`monitor.sources.list|add|update|remove` · `monitor.rules.list|save|delete|test` · `monitor.ingest` · `monitor.collect` ·
`monitor.process` · `monitor.leads.list|get|set_status|note|delete` · `monitor.report` · `monitor.export` ·
`monitor.evaluate` · `monitor.purge` · `monitor.erase_author` · `monitor.source_status` (клієнт повідомляє про
`unavailable`/`auth_error`). Права: керування джерелами/правилами/видаленням — `admin`; робота з лідами й експорт — `manager`;
читання — `viewer`.

## 10. Рішення, які потрібно ухвалити до запуску (ADR)

1. **Канал B (MTProto).** Чи дозволені умови Telegram для вашого сценарію? Яка правова підстава? Хто володіє акаунтом?
   Без письмового рішення канал вимкнений.
2. **Правова підстава обробки** (законний інтерес чи згода) та оцінка впливу (DPIA) для моніторингу.
3. **Політика зберігання автора:** `hash` / `raw` / `none`.
4. **Режим кваліфікації:** `rules` / `hybrid` / `llm`, бюджет на модель.
5. **Дозволені способи взаємодії** (CON-3) для вашого бізнесу й груп (правила груп).

## 11. Тестування та приймання

**Автоматизовані тести** покривають: ідемпотентність, обробку помилок Telegram (401/403/429/5xx), backoff, правила й
виключення, дедуплікацію всіх рівнів, кваліфікатор (включно з відмовою моделі та ін'єкцією в тексті), статуси й історію,
ролі, видалення/очищення, експорт без CSV-ін'єкцій, заборону автоматичного контакту, панель (безпечне відображення).

**Критерії приймання** (відповідають вашому ТЗ):

1. Адміністратор керує джерелами (додати/призупинити/видалити) з видимим статусом.
2. Повідомлення з погоджених джерел надходять і зберігаються; дубль доставки не створює дубліката.
3. Ключові слова змінюються без зміни коду; є тест правила.
4. Ліди фільтруються за категоріями та статусами; кожен має посилання на оригінал (якщо доступне) і причину відбору.
5. Повтори й близькі дублікати не створюють неконтрольованих лідів; історія збігів доступна.
6. Тимчасові збої не руйнують роботу; помилки видно в статусах і звітах.
7. Доступ до даних і секретів обмежений ролями; секрети відсутні в логах.
8. Оператор може підтвердити/відхилити лід і зафіксувати результат.
9. Автоматичні холодні повідомлення та механізми обходу обмежень **не існують і не вмикаються**.
10. Точність оцінена на погодженій вибірці; цільовий показник встановлюється після пілоту.

## 12. Етапи та орієнтовна оцінка

Оцінки приблизні (людино-дні однієї кваліфікованої людини) і залежать від результатів ADR.

| Етап | Зміст | Орієнтир |
|---|---|---|
| 1. Дослідження | Доступ до джерел, умови, ADR, DPIA, архітектурний документ | 3–5 |
| 2. MVP моніторингу | Джерела, збір, БД, правила L1 | 5–7 |
| 3. Кваліфікація | L2, дедуплікація, оцінка якості, ручна перевірка | 5–8 |
| 4. Панель | Джерела, правила, ліди, звіти, експорт | 5–7 |
| 5. Тестування й запуск | Відновлення, безпека, пілот на реальній вибірці, документація | 4–6 |
| Далі (за потреби) | PostgreSQL + черга, багато проєктів, інтеграції | окремо |

Інфраструктура MVP: 1 VPS 2 vCPU / 4 ГБ RAM, зворотний проксі з TLS, зашифровані резервні копії; ключ мовної моделі —
за режимом (`rules` — без витрат). Реальну вартість моделі можна оцінити лише після виміру потоку повідомлень.

## 13. Ризики

| Ризик | Заходи |
|---|---|
| Умови Telegram щодо збору/ШІ | ADR; канал A за замовчуванням; не копіювати зайве; мінімізація |
| GDPR / Закон № 480/2004 | Правова підстава, ст. 14, стоп-лист, строки, видалення; жодних автоматичних холодних звернень |
| Prompt injection у повідомленнях | Кваліфікатор без інструментів; валідація результату |
| Якість класифікації | Розмічена вибірка; ручна перевірка; пороги; режим `review` |
| Втрата/витік токенів | Ролі, ротація, маскування, шифровані копії |
| Групи забороняють ботів/збір | Дозвіл власників груп; перевірка правил груп |
| SQLite як вузьке місце | Етап переходу на PostgreSQL за вимірюваним навантаженням |

## 14. Що потрібно від замовника

1. Токен **окремого Telegram-бота** (BotFather) для моніторингу, доданого у погоджені групи/канали з правом читати
   повідомлення (режим приватності вимкнено або права адміна).
2. Перелік джерел із підтвердженим правом участі (посилання або id) та контакти власників груп за потреби.
3. Сервер (VPS/хмара) з Docker, домен і TLS; резервне сховище.
4. Ключ мовної моделі (необов'язково; режим `rules` працює без нього).
5. Рішення ADR (§10), зокрема правова підстава й дозволені способи взаємодії.
6. Розмічена вибірка повідомлень (≈200–500: релевантне/нерелевантне) для оцінки якості.
7. Для каналу B (лише після схвалення): окремий акаунт оператора та `api_id/api_hash` від самого оператора.

**Не потрібні й не використовуватимуться:** придбані акаунти й сесії, пули проксі, ферма телефонів.
