# Зведений огляд: системи моніторингу Telegram і лідогенерації

**Призначення.** Єдиний документ для вивчення: як, найімовірніше, влаштовані системи, що стежать за Telegram-групами та
контактують з авторами повідомлень; що з цього технічно реально; де ризики; що кажуть правила та право. Документ зводить
чотири незалежні матеріали, які зібрав замовник, і чесно показує, де вони збігаються, а де суперечать одне одному.

**Супутній документ:** [`TZ-telegram-monitoring.md`](TZ-telegram-monitoring.md), технічне завдання на власну систему,
побудоване з урахуванням усього нижче.

## Як читати: рівні достовірності

| Позначка | Значення |
|---|---|
| ✅ | Збігається в кількох незалежних матеріалах і відповідає загальновідомій поведінці Telegram |
| ⚠️ | Заявлено одним матеріалом або залежить від версії/політики, що змінюється; потребує перевірки |
| ❓ | Здогад або реконструкція, не підтверджена |
| ❌ | Суперечить іншим матеріалам або виглядає перебільшенням |

**Обмеження цього огляду.** Матеріали містять посилання на першоджерела (Telegram, ÚOOÚ, юридичні огляди). Я **не зміг
їх перевірити**: домен `core.telegram.org` недоступний із середовища, де готувався документ. Усі тези про умови Telegram
і чеське право слід звірити з першоджерелами та юристом до ухвалення рішень. Це не юридичний висновок.

## 1. Підсумок

1. ✅ Типова система це **серверна програма**, а не ферма телефонів: авторизовані користувацькі сесії (MTProto-клієнт,
   напр. Telethon/Pyrogram/TDLib) читають повідомлення з груп, куди акаунт має доступ, відбирають за ключовими словами,
   пишуть у БД і передають у чергу звернень.
2. ✅ **Моніторинг і звернення це різні ризики.** Збір і фільтрація технічно прості й добре працюють. Небажані перші
   особисті повідомлення незнайомцям це те, що ламає систему: скарги → обмеження → бани.
3. ✅ Паузи між повідомленнями, ротація акаунтів, старі телефони, Telegram Web **не гарантують безпеки**. Антиспам
   спирається на скарги отримувачів і поведінку, а не лише на частоту запитів.
4. ✅ **Файл сесії це пароль до акаунта.** Його витік означає повну компрометацію акаунта й листування.
5. ✅ ID користувача однаковий для всіх акаунтів, але службовий `access_hash` прив'язаний до сесії. Тож «одні читають, інші
   пишуть» технічно обмежене: другий акаунт може не мати змоги написати людині, якої не бачив.
6. ✅ Офіційний **Bot API** безпечний для моніторингу дозволених груп (бот доданий і має право бачити повідомлення), але
   **не може першим писати довільній людині**.
7. ⚠️ Правила Telegram забороняють спам/флуд (безстрокове блокування) і накладають обмеження на збір контенту; наскільки
   саме це стосується читання публічних груп, матеріали розходяться (див. §7).
8. ✅ Для ЄС/Чехії: збір персональних даних регулює GDPR, а **надсилання комерційних повідомлень окремо** потребує
   попередньої згоди (Закон № 480/2004 Coll.). «Публічне» не означає «можна розсилати».
9. ✅ Економіка автоматичних холодних звернень нестійка через вибування акаунтів (burn rate) і скарги.
10. **Висновок:** безпечна й законна версія ідеї це **моніторинг + кваліфікація + людина вирішує, як і чи контактувати**,
    без автоматичних холодних DM, без ротації акаунтів і без маскування. Саме так задумано ТЗ.

## 3. Реконструкція архітектури (спільне ядро матеріалів)

```
 Список груп / джерел, доступних акаунту
                │
                ▼
 Авторизовані клієнтські сесії  ── (файл сесії = секрет)
                │
                ▼
 Потік нових повідомлень (події, не повторне скачування історії)
                │
                ▼
 Нормалізація + фільтр (ключові слова, виключення, контекст)
                │
                ▼
 Дедуплікація  →  БД (PostgreSQL/SQLite)  →  Картка потенційного клієнта
                │
                ▼
 Перевірка оператором  ──►  Модуль звернень (черга, статуси, відповіді, відмови)
```

Статус: ✅ для збору/фільтрації/БД; ❓ для деталей модуля звернень у конкретної системи знайомого (реконструкція).

**ШІ не обов'язковий** (М3): відкриті приклади працюють на списку слів. Контекстний аналіз — покращення якості, а не
вимога; водночас застосування ШІ до контенту Telegram потребує окремої перевірки умов платформи (М3, ⚠️).

## 4. Bot API проти клієнтського MTProto

| | Bot API | Користувацький MTProto-клієнт |
|---|---|---|
| Авторизація | Токен бота від BotFather | `api_id`, `api_hash`, номер телефону, файл/рядок сесії |
| Читання груп | Лише там, де бот доданий; за Privacy Mode бачить обмежене, повний потік після вимкнення режиму або прав адміна ✅ | Усе, що бачить акаунт-учасник ✅ |
| Канали | Через права адміністратора бота ⚠️ | Усе, що бачить акаунт |
| Перше повідомлення людині | **Не може** (потрібна дія користувача, напр. `/start`) ✅ | Технічно може, але це зона антиспам-ризику ✅ |
| Ризик для особистого акаунта | Немає (це окремий бот) | Є: сесія діє від імені людини ✅ |
| Умови платформи | Bot Platform Developer Terms | API Terms; неофіційні клієнти під посиленим наглядом ⚠️ |
| Типове застосування | Підтримка, сповіщення, моніторинг дозволених груп | Скрейпінг, мультиакаунтний холодний outreach |

## 5. Технічні нюанси, важливі для проєктування

### 5.1. `access_hash` і розділення ролей (М2, М3) ✅
ID сутності однаковий для різних акаунтів, але `access_hash` прив'язаний до акаунта й **не переноситься**. Наслідок: акаунт-відправник
може написати людині лише якщо (а) у неї є публічний `@username`, або (б) цей акаунт сам її «бачить» (та сама група, контакти).
Тому схема «збирачі окремо, відправники окремо» складніша, ніж здається, і не усуває ризику.

### 5.2. Помилки: ліміт API проти антиспаму (М4, М3) ✅
| | `FLOOD_WAIT_X` | `PEER_FLOOD` |
|---|---|---|
| Природа | Технічний ліміт частоти методу | Антиспам-обмеження акаунта (скарги/підозра на спам) |
| Таймер | Є (X секунд) | Немає |
| Правильна реакція | Дочекатися X і продовжити | **Зупинити контактування**, з'ясувати причину; не «перемикатися» на інший акаунт |

Ключовий висновок (М2, М4): `PEER_FLOOD` породжують **скарги отримувачів** (кнопка «Report Spam» для першого повідомлення від
незнайомця), а не частота запитів. Тому «правильні паузи» не рятують.

### 5.3. Відбитки, проксі, прогрів (М2, М4) ⚠️ (описано, **не** впроваджується)
М4 описує як «практику» маскування відбитків з'єднання, ротаційні проксі, «прогрів» нових акаунтів і використання придбаних
сесій. М2 і М3 слушно зазначають: це може подовжити життя акаунтів, але не робить дії легальними чи «невидимими», а
економічно зводиться до постійного вибування акаунтів. **Ці техніки навмисно не входять до ТЗ**: їх призначення це обхід
антиспам-захисту платформи, і вони збільшують юридичний та репутаційний ризик.

### 5.4. Ліміти офіційних ботів (М4) ⚠️
Орієнтири: ≈1 повідомлення/с у чат, ≈20/хв у групу, ≈30/с сумарно; платні трансляції існують лише для офіційних ботів і не
вирішують проблему першого контакту. Цифри слід звірити з поточною документацією Bot API.

### 5.5. Сесії як секрет (М1, М2, М3) ✅
Рядок/файл сесії дає вхід від імені акаунта. Не передавати підрядникам, не лежати відкритим на VPS без шифрування й
резервних копій, мати процедуру відкликання сесій.

## 6. Безпека від блокувань: що реально дає, а що ні

| Захід | Дає | Не дає |
|---|---|---|
| Кілька акаунтів | Розподіл навантаження, резерв | Захисту від кореляції та скарг |
| Низька частота | Менше явних спам-сигналів | Гарантії, що ніхто не поскаржиться |
| Ротація акаунтів | Продовження роботи після обмежень | Легальності; усунення причини порушення |
| Старі телефони / Telegram Web | Інший спосіб входу | Імунітету; Telegram оцінює мережу, відомості про клієнт і поведінку, а не «корпус телефону» |
| Резидентні/мобільні проксі, прогрів | Довший строк життя | Захищеності; це обхід захисту |

Єдина стійка стратегія: не створювати причини для скарг (не писати першими незнайомцям автоматично) і поважати відмови.

## 7. Правила платформи й право

### 7.1. Telegram
* ✅ API не можна використовувати для спаму/флуду; наслідок — до безстрокового блокування. Неофіційні клієнти під наглядом.
* ✅ Telegram може обробляти метадані (IP, пристрої, застосунки, історію username) для протидії зловживанням.
* ⚠️ **Скрейпінг:** М4 стверджує, що умови «прямо забороняють скрейпінг публічних груп для сторонніх баз». М3 обережніша:
  умови забороняють доступ до контенту поза законним і передбаченим використанням, окремо обмежують використання контенту
  для ШІ, але це **не проста заборона будь-якого пошуку слів**; оцінювати потрібно мету й спосіб. **Оцінка:**
  формулювання М4 перебільшене, але «група публічна, отже можна все» точно неправильне.
* ❓ Застосування ШІ до контенту: окрема перевірка умов Content Licensing перед використанням мовної моделі.

### 7.2. Чехія / ЄС (М1, М2, М4) ✅ (звірити з юристом)
* **GDPR** регулює збір і обробку (ім'я, username, ID, текст, історія). Потрібна правова підстава (ст. 6), інформування
  суб'єкта, якщо дані зібрані не від нього (ст. 14), право заперечити проти прямого маркетингу в будь-який момент (ст. 21).
* **Закон № 480/2004 Coll.** регулює *надсилання комерційних повідомлень*: потрібна попередня згода (opt-in). Виняток для
  існуючих клієнтів не стосується холодних лідів із чатів. Штрафи за порушення до 10 млн CZK (твердження М4, ⚠️ звірити).
* ⚠️ Позиція ÚOOÚ (М2, М4): навіть перше повідомлення «чи можна надіслати пропозицію?» вважається комерційним. Тобто
  «запитати згоду» холодним DM теж ризиковано.
* ✅ **Публічність даних сама по собі не дає права на розсилку** (М1, М3).
* ⚠️ Мова про B2B: за М4 вимога поширюється і на юридичних осіб.

## 8. Ресурси та економіка

**Інфраструктура для моніторингу тексту (без обходу захисту)** — малі потреби:

| | Прототип | Підтримуваний продукт |
|---|---|---|
| Сервер | 1 VPS, 1–2 vCPU, 2–4 ГБ RAM | 2–4 vCPU, 4–16 ГБ; розмір визначати за виміряним потоком |
| Сховище | SQLite/PostgreSQL | PostgreSQL + резервні копії + строки видалення |
| Фільтрація | Слова + виключення | Контекст, дедуплікація, контроль якості |
| Інтерфейс | Сповіщення/таблиця | Панель/CRM |
| Телефони | Не потрібні для API-архітектури (М2, М3) | — |

**Головні витрати це не «ферма», а супровід:** поновлення доступу до груп, шум, дублікати, безпека сесій, скарги, юридична
відповідність, ручна перевірка. Розраховувати треба від повідомлень/добу, глибини історії, кількості сесій, строку
зберігання й складності фільтрації (М3).

**Unit-економіка холодного outreach (М4, ⚠️):** якщо акаунти-відправники вибувають після 10–15 повідомлень, вартість
залученого ліда включає вартість акаунтів, проксі й серверів і в багатьох нішах перевищує маржу. Конкретні ціни на
акаунти в огляді не наводяться навмисно.

## 9. Де матеріали розходяться або мають прогалини

| Тема | Розбіжність | Оцінка |
|---|---|---|
| Ферма телефонів | М1: «може бути»; М2/М3: не потрібна, достатньо сервера та сесій | ✅ М2/М3 правильніші |
| «Бан телефона» | М4: фізичний пристрій захищає лише від апаратного бана; М2: Telegram дивиться на мережу/відбиток | ✅ Збігаються: телефон не панацея |
| Заборона скрейпінгу | М4 категорична, М3 обережна | ❌ М4 перебільшує, див. §7.1 |
| Потрібен ШІ? | М3: ні | ✅ слова + виключення працюють; ШІ — опція |
| Безпека ротації | М1/М3: не доводить захищеності; М4: описує як практику | ✅ не доводить |
| Рівень впевненості в деталях системи знайомого | Усі: реконструкція | ❓ жоден матеріал не бачив його код |
| Ціни/кількості/штрафи | Окремі числа лише в М4 | ⚠️ потребують перевірки |
| Правова класифікація запиту згоди | М2, М4: комерційне повідомлення; М1: не уточнює | ⚠️ звірити з ÚOOÚ/юристом |

**Прогалини в усіх матеріалах:** немає виміряних даних про реальні частоти бану; немає перевірки на практиці описаних
систем; не розглянуто конкретний тип бізнесу замовника та його правову підставу; не розглянуто умови конкретних груп
(правила груп можуть забороняти ботів і збір).

## 10. Чек-лист оцінювання чужої системи (об'єднаний)

Не просити коди входу та файли сесій. Просити демонстрацію та знеособлені показники.

| Що уточнити | Що це покаже |
|---|---|
| Бібліотека/схема: Bot API, MTProto (яка), браузерна автоматизація | Реальний тип системи |
| Ролі акаунтів: хто читає, хто пише | Чи є розділення і як вирішена проблема `access_hash` |
| Шлях одного повідомлення від групи до результату | Чи відповідає факт описаному |
| Знеособлені журнали помилок за 30 днів, зокрема `PEER_FLOOD` і `FLOOD_WAIT` | Реальна стабільність; чи купують нові акаунти замість заблокованих |
| Хто надсилає перше повідомлення: людина чи скрипт | Головний ризик |
| Спосіб передачі контакту: за `@username` чи за ID | Адресованість між акаунтами |
| Глобальний ліміт на контакти з людиною, повторні звернення | Контроль настирливості |
| Стоп-лист: чи спільний для всіх акаунтів, реакція на «не пишіть» | Чи можуть різні акаунти писати тій самій людині |
